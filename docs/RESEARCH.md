## 行车记录仪工具调研

CONTEXT SHIFT THAT DEFINES THIS SPACE: Since Tesla firmware 2025.44.25 (2025 Holiday Update, HW3+), TeslaCam embeds per-frame telemetry as SEI (Supplemental Enhancement Information) NAL units inside the H.265 video stream. Tesla published the official decoder at github.com/teslamotors/dashcam (363 stars): dashcam.proto protobuf schema, sei_extractor.py CLI, dashcam-mp4.js parser, and a drag-drop SEI Explorer web player at teslamotors.github.io/dashcam. The SeiMetadata message fields are exactly: version(uint32), gear_state(enum GEAR_PARK/DRIVE/REVERSE/NEUTRAL), frame_seq_no(uint64), vehicle_speed_mps(float), accelerator_pedal_position(float), steering_wheel_angle(float), blinker_on_left(bool), blinker_on_right(bool), brake_applied(bool), autopilot_state(enum NONE/SELF_DRIVING/AUTOSTEER/TACC), latitude_deg/longitude_deg/heading_deg(double), linear_acceleration_mps2_x/y/z(double). Note SEI has NO SOC, power, elevation, odometer, or temperature — that's the TeslaMate advantage. SEI absent when parked (Sentry clips may lack it). Second shift: firmware 2026.20 (June 2026) encrypts dashcam clips BY DEFAULT with a key tied to the Tesla account; Tesla launched dashcam.tesla.com, a web viewer that decrypts locally after Tesla-account login; encryption can be disabled in Controls > Safety > Encrypt Dashcam Recordings. Any new tool must handle encrypted clips or instruct users to disable encryption (ExportDash already does in-browser decryption).

RECORDING FORMAT: USB is exFAT (128KB clusters), TeslaCam/ root with RecentClips/ (rolling ~1h buffer, flat files), SavedClips/ and SentryClips/ (one folder per event named YYYY-MM-DD_HH-MM-SS containing the surrounding ~10 min of clips, an event.json sidecar — timestamp, city, est_lat/est_lon, reason e.g. sentry_aware_object_detection/user_interaction_dashcam_icon_tapped, camera — and thumb.png). Clips are 1-minute MP4 chunks per camera named YYYY-MM-DD_HH-MM-SS-{front|back|left_repeater|right_repeater|left_pillar|right_pillar}.mp4 (Cybertruck/Plaid add a 7th rear-backup stream). moov atom is at file END (recovery-relevant; also breaks naive progressive streaming). HW3 (4 cameras): 1280x960 all cameras, ~36 fps (measured 36.019); originally H.264, switched to HEVC/H.265 in later firmware (~2023) — the codec is firmware-dependent, not hardware-dependent, so a viewer must probe per file. HW4/AI4 (6 cameras incl. B-pillars, V10+ firmware exposes pillars): H.265; front 2896x1876 @ ~30fps (early HW4 firmware exported 1448x938 and 24fps; sources conflict 24 vs 30fps across firmware), back/left_repeater/right_repeater 1448x938 @ ~30fps; pillar cams 1448x938. HEVC breaks Chrome playback without platform HEVC decode — a recurring pain point across all web viewers.

TOOL LANDSCAPE (details in projects array): RedDash (reddash.app) is a commercial iPhone/iPad app (Pro Lifetime $9.99 or $0.99/mo, v1.2.2 Jul 2026, dev 刚 熊) plus a free browser viewer; it reads footage directly off the USB drive via Lightning/USB-C without copying, plays 4-6 cams synced, parses event.json for Sentry trigger reasons, and overlays SEI telemetry (speed, steering-angle visual, accelerator/brake, gear, AP/FSD status, GPS+heading, 3-axis accel) in a "Digital Dashboard"; export layouts: 2x2 grid, cinematic PiP, cockpit, sidebar, 9:16 social-safe (TikTok/Reels safe zones), raw no-re-encode batch export. Its telemetry is entirely from Tesla's embedded SEI — it has no external data source. Sentry-Six/Sentry Studio (Electron, MIT, free) was first-to-market with a SEI telemetry dashboard overlay and adds GPU export (NVENC/AMD/QSV/Apple Silicon), blur zones, GPS minimap, 13 languages; its ecosystem includes a Raspberry-Pi smart USB drive with auto-archive and an iOS companion. ExportDash (MIT, Next.js, 126 stars) and NateMccomb/TeslaCamViewer (MIT, browser, AI plate-blur via WASM YOLOv11n/ESRGAN) are the strongest open-source browser references; DeaglePC TDashcamStudio (AGPL, Tauri, EN/CN) pioneered the speed-curve-in-scrubber idea. ehendrix23/tesla_dashcam (Python CLI, 734 stars, last stable v0.1.21 ~Dec 2023) remains the layout-richest batch composer (FULLSCREEN/MOSAIC/PERSPECTIVE/CROSS/DIAMOND/HORIZONTAL, per-camera scale/position, motion-only fast-forward, folder-watch monitor mode) but has no telemetry. Commercial generic option: Telemetry Overlay ($199, goprotelemetryextractor.com) explicitly supports TeslaCam SEI AND TeslaMate CSV exported via Grafana, with 40+ gauges and transparent-overlay export — it is the only existing tool that combines both sources, but requires manual CSV export and manual time alignment. time4tea/gopro-dashboard-overlay is the open-source analog (GPX/FIT input, XML layouts). Older/simpler viewers (Blazor TeslaCamPlayer, teslacam-browser CC0 238 stars, Microsoft Store TeslaCam, TCam UWP, Mac Sentry Viewer, web players teslacam.xyz/tesclip.com/sentrycam.appspot.com) do sync playback only, no telemetry, mostly stale. Tesla's own in-car viewer + mobile app now show the telemetry overlay too, and downloaded app clips retain SEI.

GAP ANALYSIS FOR OHMYTESLA: no tool today joins SEI frame data with a longitudinal database. SEI gives 30-36Hz precision but only while driving and only post-2025.44.25; TeslaMate Postgres (positions table ~1Hz: speed, power kW, SOC, elevation, lat/lon, battery_heater, outside_temp; drives, charges, geofences tables) covers every car since 2019 and adds SOC/power/elevation/temps that SEI lacks. Clip filename wall-clock + SEI GPS can be cross-correlated against TeslaMate positions to auto-align clocks. That fusion — plus drive-centric browsing (pick a drive in TeslaMate, see its footage) — is unoccupied territory.

**建议：**
- Parse SEI with Tesla's official schema: vendor github.com/teslamotors/dashcam's dashcam.proto and follow dashcam-mp4.js / sei_extractor.py for NAL extraction; use protobufjs client-side (ExportDash/teslanav-viewer precedent) or Python server-side. frame_seq_no gives exact per-frame ordering; vehicle_speed_mps is m/s (convert), autopilot_state distinguishes NONE/TACC/AUTOSTEER/SELF_DRIVING.
- Ingest-once architecture: since OhmyTesla already runs Postgres, add tables (clips, clip_frames_telemetry or downsampled 1Hz clip_telemetry, events) and extract SEI at import time rather than on every playback — enables SQL joins against TeslaMate drives/positions/geofences and fast analytics (FSD%, disengagements, hard-braking search).
- Codec strategy is the #1 web-viewer pitfall: HW3 pre-2023 clips are H.264 (plays everywhere), everything since is HEVC. Chrome/Edge only decode HEVC with platform hardware support; Chromium-in-Electron often can't. Probe codec per file (ffprobe/mp4box), play natively when possible, and fall back to on-the-fly server ffmpeg transcode or WASM decode. Note moov atom at file end — either fast-start remux on ingest or serve whole files.
- Time model: treat clip filename (YYYY-MM-DD_HH-MM-SS local time) as coarse start, refine with SEI GPS-vs-TeslaMate-positions cross-correlation; interpolate TeslaMate 1Hz data (positions: speed, power, SOC, elevation) with monotonic interpolation onto video PTS; beware TeslaMate timestamps are UTC while clip filenames are car-local time.
- Composition engine: for burned exports use ffmpeg filtergraphs (xstack/overlay/drawtext) with hwaccel selection per platform (NVENC, QSV/VAAPI, VideoToolbox) exactly as tesla_dashcam does — its layout definitions (MOSAIC/CROSS/DIAMOND/etc.) are a proven taxonomy to copy; render telemetry gauges to a transparent frame sequence or Canvas-captured overlay track composited over the camera grid.
- For instant in-browser clip export use WebCodecs + mp4-muxer (ExportDash/teslanav-viewer stack); keep server ffmpeg for multi-minute merges and 6-camera 2896x1876 loads where browser memory dies.
- Maps: MapLibre GL JS or Leaflet with OSM tiles; draw route from TeslaMate positions (works even without SEI), color segments by autopilot_state when SEI present; for exported video pre-render map tiles server-side (gopro-dashboard-overlay approach) to avoid live-tile licensing/perf issues.
- License hygiene: MIT references you may read/borrow from: ExportDash, Sentry-Six, NateMccomb TeslaCamViewer, teslanav-viewer; AGPL-3.0 (DeaglePC) and source-available (bt1142msstate) — ideas only, no code; tesla_dashcam is a CLI you could even shell out to for batch composition.
- Plan for encryption (2026.20+ default-on): detect .mp4 files that fail to parse as clear MP4, surface a clear UX explaining the Controls > Safety toggle, and investigate the dashcam.tesla.com local-decryption flow (account-tied key) that ExportDash reverse-implemented — otherwise every new-firmware user's first experience is 'broken files'.
- Per-camera geometry differs on HW4 (front 2896x1876 vs others 1448x938, HW3 all 1280x960, fps 36 vs ~30/24): never hardcode dimensions; probe each stream and normalize via scale filters; support 4-, 6-, and 7-camera (Cybertruck rear-backup) sets and gracefully degrade on missing angles.

## 哨兵告警方案调研

SENTRY EVENT DETECTION — GROUND TRUTH. The ONLY near-real-time source of sentry events for third parties is Tesla Fleet Telemetry. Its protobuf (teslamotors/fleet-telemetry protos/vehicle_data.proto, 874 stars) defines field SentryMode (field 65) with enum SentryModeState: Unknown/Off/Idle/Armed/Aware/Panic/Quiet. "Aware" = sentry detected motion/proximity (the event all commercial apps alert on); "Panic" = alarm. Related fields: CenterDisplay (DisplayStateLock state = someone touched a locked car, usable for break-in alerts even with sentry OFF), ChargePortLatch (used to suppress cable-plug false positives), Locked, GuestModeEnabled. Delivery semantics (developer.tesla.com): a field is sent only when interval_seconds has elapsed AND the value changed; firmware 2024.44.32+ adds minimum_delta and resend_interval_seconds. Telemetry requires: Tesla developer/partner app registration, hosted public key, VIRTUAL KEY paired to vehicle (exception: pre-2021 Model S/X on firmware 2025.20+), firmware 2023.20.6+, and a publicly reachable mTLS fleet-telemetry server (FQDN + CA cert); dispatchers: Kafka, Kinesis, Pub/Sub, ZMQ, MQTT, Redis, logger. No Premium Connectivity needed. BY CONTRAST: (a) Fleet API vehicle_data only exposes vehicle_state.sentry_mode (boolean on/off), sentry_mode_available, and center_display_state (7 = sentry showing) — NO event/Aware/alarm field exists (confirmed by TeslaMate maintainers in teslamate discussion #3292: "There is no API endpoint today that delivers this value"), so polling can never see sentry events, only arming state; (b) vehicle_data polling is also cost-prohibitive on Fleet API: $0.002/request (2 credits) → 1-min polling ≈ $86/mo vs $10/mo free credit; streaming signals cost $0.0001/signal (a SentryMode-only on-change stream costs pennies); commands $0.001, wake $0.02 (Teslemetry pay-per-use blog); (c) the legacy Owner API WebSocket stream (wss://streaming.vn.teslamotors.com, still used by TeslaMate 4.1.0-dev) carries only driving fields: speed, odometer, soc, elevation, est_heading, est_lat, est_lng, power, shift_state, range, est_range, heading — no sentry/alarm; (d) TeslaMate MQTT publishes teslamate/cars/$car_id/sentry_mode (boolean) and center_display_state at polling cadence (POLLING_ONLINE_INTERVAL=60s idle, default 15s, driving 2.5s; sentry_mode:true blocks suspend, vehicle.ex:1839) — no alarm/event topic exists; (e) Tesla's own app pushes only "Security Alerts" (alarm trigger, door/trunk opened, impact while away) and NEVER routine sentry proximity/motion events — this gap is the entire market for these apps. SENTRYPRO (sentrypro.app, iOS+Android, "Approved Tesla Fleet API developer"): detects events via Fleet API/Fleet Telemetry ("receives events from Tesla's Fleet API when Sentry Mode records activity"); virtual key required, MCU2 S/X needs 2025.20+, MCU1 unsupported — signature matches Fleet Telemetry SentryMode=Aware detection. Pricing $5.99/mo, $49.99/yr, $133.99 lifetime, 7-day trial, all vehicles on one sub. Features: push "within seconds", iOS Critical Alerts (Auto = escalate after 90s of continued activity, or Always), 15-second continuous-event dedup, auto-honk/flash/boombox deterrents, backend-side sentry scheduling (works with phone off), activity feed, battery data (sentry ≈150W on 2024.38+, ~3.6 kWh/24h = 4-8% pack/day). Admits 2+ min delays in poor LTE and cannot distinguish automatic vs event-driven activations. SENTRYALERT (sentryalert.app): explicitly "streams Sentry Mode events in real time via Tesla Fleet Telemetry", auto telemetry setup, push per event, remote honk/flash, 5 vehicles/account, 30-day filtered event history, 7-day trial then monthly/annual sub. **建议：**
- Event source: use Fleet Telemetry, not polling. vehicle_data has no sentry-event field (only sentry_mode bool + center_display_state=7), so polling is architecturally blind to events, adds up to 60s lag through TeslaMate's online interval, and costs $0.002/request on Fleet API (~$86/mo at 1-min cadence) vs $0.0001/signal for on-change streaming that fits inside Tesla's $10/mo free credit.
- Concrete telemetry config: fleet_telemetry_config with fields {SentryMode:{interval_seconds:1..30}, CenterDisplay:{interval_seconds:30}, ChargePortLatch:{interval_seconds:30}} — values transmit only on change, so a 1s interval on SentryMode is nearly free and gives 1-5s end-to-end latency on good LTE (worst case minutes in poor coverage; both SentryPro and SentryGuard document this).
- Three deployment tiers for a self-hosted TeslaMate-based web app: (1) EASY — point the car's telemetry at MyTeslaMate (free tier) and consume their MQTT/streaming re-emission next to the existing TeslaMate integration; (2) FULL CONTROL — self-host teslamotors/fleet-telemetry (Go) with the MQTT dispatcher into the same broker TeslaMate already uses; requires Tesla developer app registration, hosted public key, FQDN + CA-signed TLS + mTLS, and a virtual key on the vehicle; (3) REUSE — SentryGuard is AGPL-3.0 (same license as TeslaMate) and its NestJS handlers (Aware detection, DisplayStateLock break-in logic, ChargePortLatch debounce) can be embedded or run as a sidecar docker-compose service.
- Detection state machine: alert on Armed/Idle/Quiet→Aware; critical-alert on →Panic; debounce consecutive Aware within 15s into one incident; escalate if activity persists 90s; suppress when is_user_present or a charge-latch event correlates within the verification window; record every transition with timestamps for the incident timeline.
- Battery/API cost truth for docs: sentry mode itself keeps the car awake (~150W on fw 2024.38+, 4-8% pack/day) — telemetry streaming adds nothing measurable, and polling while sentry is armed also doesn't add battery drain (car already awake, TeslaMate never suspends with sentry on) — polling's real costs are blindness to events, latency, and Fleet API fees.
- Default notification channel set for a self-hosted web app: (1) Telegram bot as the flagship default — free, instant on iOS+Android, supports actionable inline buttons (honk/mute), proven by SentryGuard/MyTeslaMate; (2) Web Push for the app's own PWA — free, self-generated VAPID, no third-party account, but document iOS 16.4+ requirements (must be installed to Home Screen, permission requested from a user tap); (3) ntfy for the self-hosted crowd — no account needed, HTTP POST, but self-hosted servers need upstream-base-url=ntfy.sh relay for instant iOS delivery; (4) SMTP email as universal fallback. Offer Pushover ($5 one-time, most reliable mobile push) and Discord webhook as cheap options, and integrate Apprise (BSD-2, 100+ services, single-URL config) as the extensibility layer instead of hand-writing more integrations. Avoid Gotify as a default: no official iOS client.
- Also publish each sentry incident to MQTT (TeslaMate-topic style) so Home Assistant/Node-RED users can build their own automations — this matches the existing TeslaMate integration culture (the official docs' Node-RED Telegram flow) and costs nothing.
- Latency budget to advertise honestly: car→Tesla→your telemetry endpoint typically 1-3s, total push under 5s on good LTE; state clearly (as SentryPro does) that poor cellular coverage can delay alerts by minutes and that MCU1 cars are unsupported and MCU2 S/X need fw 2025.20+ with virtual-key exemption rules for pre-2021 S/X.

**建议：**
- Build ingestion on Tesla Fleet Telemetry (push/streaming) as primary, with Owner-API polling only as legacy fallback — this eliminates the entire TeslaFi-style sleep-management problem class and gives BMS-grade signals that Teslascope/Tessie already use for battery health; keep a TeslaMate-style polling adapter for older firmware.
- Implement battery health as a multi-estimator pipeline, not one number: (a) TeslaMate derived-efficiency estimator (charge_energy_added / rated-range delta, filtered charges >10min end<=95%, rolling avg of last ~100 points vs historical max — SQL already in grafana/dashboards/battery-health.json in the local repo), (b) range-ratio estimator, (c) Fleet Telemetry BMS pack-energy signals when available, (d) optional Scan-My-Tesla/CAN import for ground truth. Show confidence bands and let users pin 'capacity when new' — SMT removed its degradation number because factory settling made single-source numbers wrong; learn from that.
- Ship an alerts + automations engine early (triggers: geofence, plugged-in, SOC, time, Sentry; actions: full command set). This is the single biggest functional gap between TeslaMate and Tessie/Teslascope and the top reason users pay subscriptions.
- Expose three integration surfaces from day one: MQTT (retain TeslaMate compatibility for Home Assistant/ABRP bridges), a REST API with PAT/OAuth scopes, and a telemetry-export format consumable by dashcam viewers (Sentry Clip Viewer already integrates TeslaMate/Tessie data) — being the best data hub is cheaper than building every UI.
- Write importers for TeslaFi CSV, Tessie export, TezLab and Teslascope archives (Tessie proves import is a growth lever), and an exporter so users never feel locked in — key open-source differentiator.
- Do not rebuild route planning; integrate with ABRP via the established teslamate-abrp MQTT bridge pattern, but keep a local consumption model (Wh/km vs speed/temp/elevation from logged drives) for in-app range projection.
- Fleet comparison features (degradation percentile matched by model/pack/odometer/climate, firmware rollout tracking) require aggregated multi-user data: design an opt-in anonymized telemetry pool now (self-hosters push summary stats to a community service), since this is the one feature class pure self-hosting cannot deliver.
- Treat cost tracking as first-class schema: per-geofence tariffs, TOU windows, tiered rates, Supercharger invoice ingestion (Teslascope does invoice sync via Tesla account), and business/personal drive tagging for tax-ready mileage export.
- For China support, plan for the separate China Fleet API region, data-residency constraints, and WeChat mini-program delivery; feature parity references are 小特 (community + charging map + ground-lock unlock) and offline BLE key (小特钥匙).
- Command execution must implement Tesla Vehicle Command Protocol signing (Tessie monetizes just this); consider vendoring Tesla's official vehicle-command Go proxy or an Elixir equivalent rather than reimplementing.
- Mobile/watch presence matters: minimum viable = PWA + Lock Screen Live Activity substitute, home-screen widgets, and a Watch complication for SOC; Stats app shows deep OS integration (Siri Shortcuts, widgets) drives one-time-purchase loyalty.
- Keep Grafana as the power-user layer but put a curated first-party UI in front of the top 6 views (overview, drive detail, charge detail, battery health, costs, software updates) — Grafana UX is the most cited TeslaMate adoption barrier vs Tessie.

## TeslaMate 内部结构

TeslaMate (repo at <repo>/teslamate, VERSION 4.1.0-dev) is an Elixir/Phoenix 1.7 + LiveView app that logs one or more Tesla vehicles by combining Owner-API polling (state-dependent intervals, 2.5s while driving) with the ~1 Hz Owner streaming WebSocket, persists everything to Postgres in metric units (km/h, kW, km, °C, bar, microsecond timestamps), republishes a live car summary to MQTT under teslamate/cars/$car_id/..., and ships 23 provisioned Grafana dashboards that read the Postgres DB directly. Companion services are expected to integrate via MQTT (live state) and direct Postgres reads (history); the app itself exposes almost no HTTP API (only PUT /api/car/:id/logging/{resume,suspend}, GET /drive/:id/gpx, GET /health_check). The web UI is translated to Simplified and Traditional Chinese. For dashcam overlay: during a streaming drive the positions table gets ~1 row/second containing date (ms precision), lat/lon, speed (int km/h), power (int kW), battery_level, elevation (int m), odometer (km) — but no heading column; heading exists only on the live MQTT topic or must be derived from consecutive coordinates.

With car_settings.use_streaming_api=true (default) the streaming socket delivers ~1 frame/second while driving; each frame with shift_state in D/N/R inserts one positions row via create_position(%Stream.Data{}) containing ONLY: date (ms), latitude=est_lat, longitude=est_lng, power (int kW), speed (mph->km/h rounded int), battery_level=soc, elevation (int m, from stream), odometer (km). - DASHCAM OVERLAY DATA AVAILABILITY: per-second during-drive telemetry lives in positions (JOIN drives ON positions.drive_id) with speed/power/battery_level/elevation/lat/lon/odometer at ~1 Hz (stream mode). **建议：**
- Integrate live state via MQTT (teslamate/cars/$car_id/#) and history via read-only Postgres queries on positions/drives/charging_processes/charges — this is exactly how all blessed community projects work; do not call TeslaMate HTTP endpoints for data (there are none) and never write to its tables except the documented cost-update pattern (charging_processes.cost).
- For dashcam telemetry overlay, query positions filtered by drive_id (drives.start_date/end_date bound the video window): you get ~1 Hz speed (km/h), power (kW), battery_level, elevation, lat/lon. Compute heading client-side from successive coordinates (atan2 of deltas) because positions has no heading column; if you need true heading, capture the MQTT 'heading' topic in real time alongside the recording, or subscribe your own consumer that archives it.
- Interpolate/carry-forward usable_battery_level, temperatures, and range values across stream-inserted rows — they are only present on sparse poll-based rows; treat NULLs in those columns as 'unchanged since last poll', not missing data.
- Use a dedicated read-only Postgres role for companion services and expect the schema to move (migrations auto-run on every TeslaMate upgrade at container start; e.g. tokens moved to a 'private' schema, positions indexes rewritten in 2025-2026 migrations). Pin queries to columns, not to indexes or physical layout, and gate upgrades in staging.
- If subscribing MQTT, set clean-session consumers to tolerate retained messages (all topics except 'healthy' are retained), key on car_id = cars.id from the DB (not VIN), and honor MQTT_NAMESPACE if the deployment sets one.
- For sentry/alarm-adjacent features, rely on the MQTT sentry_mode topic (true/false, retained) — sentry status is never written to Postgres, so any historical sentry timeline must be recorded by your own MQTT archiver.
- If the deployment must move off the Owner API (business fleet accounts), keep TeslaMate unforked and switch endpoints via env only: TOKEN + TESLA_API_HOST/TESLA_AUTH_HOST/TESLA_AUTH_PATH (MyTeslaMate/Teslemetry) and TESLA_WSS_HOST/TESLA_WSS_USE_VIN for reconstructed streaming; note Fleet Telemetry-based streams are coarser (>=1 min) which degrades the per-second positions density that video overlay depends on.
- Chinese-market deployments work out of the box: token region auto-detection picks owner-api.vn.cloud.tesla.cn and streaming.vn.cloud.tesla.cn, and the web UI already ships zh_Hans/zh_Hant translations — send Accept-Language: zh or ?locale=zh_Hans rather than patching the UI.

The old free "Discovery tier" (2023) was superseded by this credit model. Note asymmetry: polling vehicle_data is ~300x costlier per datum than telemetry signals; 1-min polling ≈ $0.12/hr of driving. vehicle_data endpoint takes ?endpoints=... (semicolon-separated) with groups: charge_state, climate_state, closures_state, drive_state, gui_settings, location_data (lat/lon moved here in 2023.38+ firmware — drive_state no longer returns coordinates without it), vehicle_config, vehicle_state, vehicle_data_combo. Other key endpoints: /wake_up, command endpoints (must be routed through the signed-command proxy for modern cars). Rate limiting exists (TeslaMate handles Fleet API EXCEEDED_LIMIT with 15-min backoff). REGIONS: NA, EU, and China. China is a fully separate universe: separate portal developer.tesla.cn (requires tesla.cn account + a +86 phone number), separate base URL https://fleet-api.prd.cn.vn.cloud.tesla.cn, docs at developer.tesla.cn/docs/fleet-api. Third-party bridges (e.g. Tessie) advertise automatic NA/EU/China routing.

(2) FLEET TELEMETRY (github.com/teslamotors/fleet-telemetry, Go, 874 stars, pushed 2026-07-15, actively maintained). Server reference implementation of Tesla's vehicle→server push protocol: vehicles open a persistent mTLS WebSocket to your server and push protobuf frames. Self-host requirements: FQDN + valid TLS cert with mTLS termination, public key at the .well-known path, virtual key paired, per-vehicle config pushed via fleet_telemetry_config endpoint (fields + interval_seconds each), firmware ≥2023.20.6 (older Model S/X unsupported until ~2025.20; as of July 2025 effectively all vehicles supported). Dispatchers: Kafka (preferred), Kinesis, Google Pub/Sub, ZMQ, MQTT, Redis Pub/Sub, stdout logger. Streams: V (vehicle data), alerts, errors, plus optional connectivity events (proxy for online/asleep state). Field catalog ~407 fields (protos/vehicle_data.proto); notable: Location(21), GpsState(22), GpsHeading(23), VehicleSpeed(4), Soc(8), BatteryLevel(42), EstBatteryRange(40), Odometer(5), Gear(10), DetailedChargeState(179) (enum Disconnected/NoPower/Starting/Charging/Complete/Stopped), ACChargingPower(37)/DCChargingPower(35), ChargeLimitSoc(38), TimeToFullCharge(43), InsideTemp(85)/OutsideTemp(86), Locked(59), DoorState(58) (Doors msg: DriverFront/DriverRear/PassengerFront/PassengerRear/TrunkFront/TrunkRear), SENTRYMODE(65) with enum SentryModeState: Off/Idle/Armed/AWARE/PANIC/Quiet — SentryModeStateAware/Panic are the alarm-relevant transitions; also ServiceMode(159), ValetModeEnabled(226), PinToDriveEnabled(124), GuestModeEnabled(123), TpmsHard/SoftWarnings(224/225), ForwardCollisionWarning(130), LocatedAtHome/Work/Favorite. There is NO dedicated "sentry event with camera/reason" signal — SentryMode state changes are the closest realtime security telemetry. Minimum interval is 1s for most fields (Location, VehicleSpeed, Soc, SentryMode, Gear, DetailedChargeState all min 1s; Odometer 10s; limits/defaults enumerable at api.teslemetry.com/fields.json). Latency: push over persistent WebSocket, effectively ~1–2s end-to-end when the car is online (vehicle transmits at the configured cadence; one integrator reports ~500ms internal send cadence). Billing: streaming signals are billed by Tesla per-signal even to a self-hosted server (the repo ships signal-count metrics explicitly "to identify approximate billing", incl. per-VIN tracking) — but at 150k signals/$1, ~5 fields at 10s intervals is ~$0.86/mo/car, easily inside the $10 credit; Location@1s continuous while driving ≈ 100k signals/mo ≈ $0.72.

(3) LEGACY OWNER API (owner-api.teslamotors.com): zombie but alive for individuals in Aug 2026. Officially shut down for Business Fleet accounts (their cars return errors pointing to Fleet API); for individual consumer accounts it still works, including the old 1 Hz driving-telemetry WebSocket stream (streaming.vetted... "streaming API"), which TeslaMate 4.x still uses by default. Tesla has been tightening it: auth now requires TLS1.2+/HTTP2 (a June 2026 change briefly broke TeslaMate until a patched release), commands rejected on some vehicles, no announced end date for individuals but consensus is it can die any time. 2020-and-older Model S/X don't support the new streaming replacement, complicating migration.

(4) BLE — teslamotors/vehicle-command (Go, 685 stars, pushed 2026-07-31, active). Implements the Vehicle Command Protocol over both Fleet API REST and direct BLE. tesla-keygen creates a NIST P-256 key; enroll via `tesla-control -ble add-key-request public_key.pem owner cloud_key` + NFC-card tap on console; thereafter most commands (lock/unlock, climate, charging, trunk, wake) work purely locally over BLE with zero Fleet API involvement and ZERO fees, no internet. Does not run on Windows (Go BLE library limitation); Linux/BlueZ (incl. Raspberry Pi) and macOS work. Wake over BLE works (this is how esphome-tesla-ble and similar keep cars controllable without paying $0.02/wake). BLE gives commands, not telemetry streams (limited state reads only). Range = Bluetooth (~5–20m), so it suits home/garage automation, not remote alerts.

(5) TESLACAM USB FORMAT. Drive must be exFAT (Tesla-formatted: 128KB clusters); root folder TeslaCam/ with RecentClips/ (flat rolling ~1hr dashcam buffer, oldest auto-deleted), SavedClips/ and SentryClips/ (each event = subfolder named YYYY-MM-DD_HH-MM-SS containing up to ~10 min of pre-event footage). Files: one MP4 per camera per minute, named YYYY-MM-DD_HH-MM-SS-<camera>.mp4 with camera ∈ {front, back, left_repeater, right_repeater} on HW3 (4 cams) and additionally {left_pillar, right_pillar} on HW4 (6 cams; B-pillar recording shipped in 2025.14 "Spring Update", HW4-only — HW3 cars, even Ryzen-infotainment ones, never got it). Event folders contain event.json + thumb.png. event.json schema: {"timestamp":"YYYY-MM-DDTHH:MM:SS" (local), "city":"<name>", "est_lat":"<string>", "est_lon":"<string>", "reason":"<code>", "camera":"<digit string>"}. Observed reason codes: sentry_aware_object_detection, sentry_aware_accel_<value>, user_interaction_dashcam_icon_tapped, user_interaction_dashcam_panel_save, user_interaction_honk (sentry panic events also occur). camera numbering (community-reverse-engineered, treat cautiously — mappings differ between tools): 0=front, 1=fisheye, 2=narrow, 3=left_repeater, 4=right_repeater, 5=left B-pillar, 6=right B-pillar, 7=rear, 8=cabin. Codecs/resolutions actually observed: HW3 = 1280x960 all cameras, historically H.264 ~36fps, newer firmware HEVC/H.265 (players must handle both); HW4 = front 2896x1876, other cameras 1448x938, HEVC, ~24–30fps (front fps dropped vs HW3). ~15–30MB per camera-minute; a HW4 minute = 6 files. Quirks: clips are ~59s with 2–3s gaps between consecutive minute files; per-camera files for the same minute can differ slightly in length/start (align by filename timestamp + frame offsets, not by container timestamps); MP4 moov atom is written last, so the in-progress/last minute at power-cut is often corrupt/unplayable (recoverable by carving); burned-in on-video timestamps have historically been wrong (hardcoded Pacific in some firmwares) — FILENAME timestamps are the trustworthy clock; slow USB drives cause dropped/corrupt segments.

(6) CHINA. Chinese cars DO have Dashcam/TeslaCam and Sentry Mode; Tesla China's official position (Aug 2023, after sentry-related parking bans): Sentry/dashcam footage is stored ONLY on the local USB drive, never uploaded, and remote live-camera viewing from the app is disabled in China. All Chinese vehicle cloud data is stored in-country (Shanghai data center) per PIPL/data-security rules. Fleet API exists in China as a separate region: developer.tesla.cn portal (+86 phone required), base URL fleet-api.prd.cn.vn.cloud.tesla.cn; a self-hosted Chinese user must register there, and a self-hosted fleet-telemetry server for a Chinese car should be hosted reachable from China (data-residency argues for hosting in-country; also GFW reliability). BLE vehicle-command is region-independent (protocol lives in the car) and should work in China. TeslaCam USB parsing is 100% offline/local — zero regulatory or connectivity exposure, identical format worldwide.

TESLAMATE CONTEXT (local repo = 4.1.0-dev): still Owner-API-first with optional Fleet API via bring-your-own token or proxies; publishes rich MQTT topics (now incl. service_mode, window/sunroof states, software update progress); handles Fleet API rate limits. Proxy ecosystem: MyTeslaMate is no longer free (500 credits/€1; 1 command=1cr, 150 signals=1cr, 300 API calls=1cr, wake=20cr; includes fleet-telemetry→MQTT bridging and even "Sentry break-in alerts via Telegram" — a direct competitor feature); Teslemetry repositioned as paid Fleet API access layer (webhooks/SSE, fields.json catalog).

**建议：**
- (a) Realtime alerts: build on Fleet Telemetry, not polling. SentryMode(65) at 1s interval plus connectivity events gives ~1–2s push latency; a sentry-focused field set costs well under the $10/month Tesla credit (150k signals/$1). Accept telemetry either from a self-hosted fleet-telemetry server (FQDN+mTLS+virtual key, more setup) or via a proxy's MQTT bridge. Do NOT build alerts on vehicle_data polling ($0.002/poll, high latency) or on the Owner API (can die without notice).
- (b) Overlay sync accuracy: master clock = TeslaCam filename timestamps (burned-in video timestamps are unreliable, historically hardcoded Pacific). Sync source ranking: TeslaMate positions from the 1Hz Owner-API stream today; design the ingestion behind an interface so Fleet Telemetry Location@1s can replace it when the Owner API dies. Handle the known 2–3s inter-minute gaps and per-camera offsets; provide a one-time user calibration (slide overlay ±N seconds) per car.
- (c) Zero-additional-cost operation: consume TeslaMate's MQTT topics (location, speed, soc, sentry, locked, service_mode) + direct USB TeslaCam parsing — no Tesla developer account, no fees, works today. For users who outlive the Owner API, the documented upgrade path is their own free Fleet API app whose $10 credit covers a 1–2 car telemetry config, plus BLE vehicle-command for fee-free local commands/wakes.
- Architectural: treat data sources as pluggable adapters (OwnerAPI-via-TeslaMate | FleetTelemetry-self-hosted | FleetTelemetry-via-proxy | USB-TeslaCam), because the Owner API is a zombie, proxies keep changing pricing (MyTeslaMate dropped its free tier), and Tesla's per-signal billing rewards narrow field sets.
- China: ship a region flag. Chinese users need developer.tesla.cn (+86 phone) and fleet-api.prd.cn.vn.cloud.tesla.cn; remote live camera is disabled there but Sentry/TeslaCam USB recording works identically, so the USB-ingestion path is the China-safe core. Keep all video processing local (data-residency + user trust).
- TeslaCam ingestion hard requirements: exFAT reading, HEVC decode (HW4 and newer HW3 firmware), 2896x1876 front streams (transcode/downscale for web playback), tolerate missing/corrupt moov-atom clips, HW3 4-cam vs HW4 6-cam layout detection from filename suffixes, and treat event.json camera numbering as heuristic (verify against real HW4 data).
